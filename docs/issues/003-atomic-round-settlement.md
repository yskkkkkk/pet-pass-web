# 003 — 결과 확정 후 탈락 갱신 실패 시 복구할 수 없음

**우선순위:** P1

**분류:** 구현 결함 / 소수결 정산·향후 점수제 기반

**상태:** 미해결

## 근거

- `lib/game/games/minority/index.js:111-118`: 방을 `revealed`/`finished`로 확정한 다음 참가자를 탈락시킨다.
- `lib/game/games/minority/index.js:90-93`: 재시도는 방이 이미 투표 중이 아니므로 거절된다.
- `lib/game/games/minority/index.js`의 `hostState`·`playerState`: 생존자와 우승자는 결과 스냅샷이 아니라 별도로 읽은 참가자 행에서 계산한다.
- `lib/game/store.js`의 `updateRoom`과 `eliminatePlayers`는 별도 DB 요청이다.

## 재현과 영향

1. 3명이 A 1표/B 2표로 투표한다.
2. `eliminatePlayers`가 DB 오류를 던지도록 실패를 주입하고 공개한다.
3. API는 500이지만 방은 이미 `finished`, 결과의 `survivorCount`는 1이다.
4. 참가자 행은 모두 생존 상태이므로 진행자 상태의 `aliveCount`는 3이고 참가자 우승 목록에도 3명이 들어간다.
5. 다시 공개해도 409이므로 실패한 탈락 갱신을 재개할 수 없다.

위 상태를 핸들러 직접 호출과 저장소 실패 주입으로 확인했다. 일시적인 화면 불일치가 아니라 다음 조회에도 남는 저장 상태 불일치다. 같은 “방 전환 후 사람별 갱신” 패턴을 새 점수제 게임에 적용하면 칩·점수의 부분 반영으로 확장될 수 있다.

## 수정 방향

공개 결과·탈락·점수·칩 등 정산 결과를 하나의 DB 트랜잭션으로 확정하거나, 실패 후 안전하게 재개할 수 있는 명시적 정산 상태와 멱등성 계약을 도입한다. 기존 조건부 방 전환에 의한 중복 공개 방지는 유지한다. 참가자 갱신을 먼저 하는 순서 변경만으로는 반대 방향의 부분 실패를 해결하지 못한다. 002의 마감/제출 경계와 함께 설계한다.

## 완료 기준

- [ ] 탈락 갱신 실패 시 방과 참가자가 모두 기존 상태로 남거나, 복구 가능한 정산 상태로 남는다.
- [ ] 재시도·동시 공개가 점수/칩/탈락을 중복 적용하지 않는다.
- [ ] 공개 상태에서 결과의 생존자 수와 실제 생존자·우승자가 일치한다.
- [ ] 정산 중 상태 조회·다음 라운드·재시작이 부분 상태를 확정 상태처럼 사용하지 않는다.
- [ ] 각 쓰기 단계의 실패와 동시 요청을 검증하는 회귀 테스트를 추가한다.
