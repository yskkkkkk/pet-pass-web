# 001 — 문제 변경·재시작을 구분하지 못하는 투표 식별자

**우선순위:** P1

**분류:** 구현 결함 / 소수결·공통 제출 기반

**상태:** 미해결

## 근거

- `public/game/minority/play.js:55-77`: 제출과 선택 비교의 식별자가 `round`뿐이다. 같은 라운드·같은 선택이면 요청을 보내지 않는다.
- `lib/game/games/minority/index.js:38-42`: 서버도 라운드 번호만 비교하며 번호 생략까지 허용한다.
- `lib/game/games/minority/index.js:72-86`: 문제 변경은 라운드 번호를 유지하고 서버 표만 삭제한다.
- `lib/game/games/minority/index.js:121-133`: 재시작은 라운드를 0으로 되돌리지만 참가자 토큰은 유지한다.
- 계획서의 공통 입력 원칙과 구조 문서의 “지난 라운드 제출 거절” 보장이 초기화 경계를 포함하지 못한다.

## 재현과 영향

1. 휴대폰에서 1라운드 A를 선택하고 저장을 기다린다.
2. 진행자가 문제를 바꾼다. 서버 표는 없어지지만 휴대폰의 `votes.wanted()`는 여전히 `{ round: 1, choice: 'A' }`다.
3. 휴대폰은 새 문제에도 A를 선택한 것으로 표시하며 A를 다시 눌러도 POST를 보내지 않는다. 그대로 공개하면 미투표로 탈락할 수 있다.
4. 같은 멤버로 재시작해 다시 1라운드가 되어도 같은 문제가 발생한다. 초기 판의 1라운드에서 끝내면 쉽게 재현된다.

격리 실행에서 같은 값의 연속 `push`가 한 번만 전송되는 것과, 문제 변경·재시작 후 예전 `{ round: 1, choice: 'A' }` 요청이 서버에서 200으로 수락되는 것을 확인했다. 따라서 화면 초기화만 고치면 지연된 과거 투표가 새 문제에 들어가는 서버 문제는 남는다.

## 수정 방향

판 세대와 문제/입력 세대를 구별하는 식별자를 서버에서 발급하고 상태 응답·투표 요청·저장 조건에 일관되게 사용한다. 문제 변경과 재시작은 새 세대를 만들어야 한다. 클라이언트는 세대가 바뀔 때 저장/대기 중 선택을 분리하고 과거 요청의 콜백도 새 화면에 반영하지 않아야 한다. 서버의 세대 검증은 002의 원자적 제출 저장에 포함한다.

## 완료 기준

- [ ] 문제 변경 직후 선택이 비워지고, 이전과 같은 A를 눌러도 실제로 새 표가 저장된다.
- [ ] 재시작 후 같은 번호 라운드에서도 위 동작이 성립한다.
- [ ] 문제 변경·재시작 전에 보낸 지연 요청이 새 입력 세대에 저장되지 않는다.
- [ ] 같은 세대 안에서 빠르게 A→B로 바꾸는 기존 순차 전송 동작은 유지된다.
- [ ] API 회귀 테스트와 문제 변경·재시작·지연 응답을 포함한 Playwright 테스트를 추가한다.
