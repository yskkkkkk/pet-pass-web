# 002 — 제출 검증과 저장이 분리되어 마감 뒤에도 표가 바뀜

**우선순위:** P1

**분류:** 구현 결함 / 소수결·공통 라운드

**상태:** 미해결

## 근거

- `api/game.js:176-189`: 요청 시작 시 읽은 방 상태를 게임 모듈에 전달한다.
- `lib/game/games/minority/index.js:29-44`: 읽어 둔 상태를 검사한 뒤 별도 작업으로 표를 UPSERT한다.
- `lib/game/games/minority/index.js:94-117`: 표 조회·판정·방 전환도 별도 작업이다.
- `lib/game/round.js:29-36`: 새 게임용 `submitMove`에도 같은 검사-저장 간격이 있다.
- `lib/game/store.js`의 `upsertVote`·`upsertMove`는 현재 방 상태를 저장 시점에 검증하지 않는다.

## 재현과 영향

1. 3명이 모두 A를 제출한 투표 중 방을 준비한다.
2. 한 참가자의 B 변경 요청을 받아 검증까지 진행시키고, `upsertVote` 직전에 대기시킨다.
3. 진행자가 공개를 완료한다. 결과는 A 3명/B 0명이다.
4. 대기 중인 UPSERT를 재개하면 B 변경 요청은 200으로 성공한다.
5. 참가자 상태는 `me.choice: 'B'`지만 공개 결과의 `bCount`는 0이다.

메모리 저장소 작업을 지연시켜 위 순서를 재현했다. Supabase 구현도 검증과 UPSERT가 별도 요청인 구조지만 실제 Supabase에서 경쟁 상황을 실행한 것은 아니다. 공개 전 1초 유예는 요청 도착을 돕는 UI 장치일 뿐 원자적 마감을 보장하지 않는다. 향후 경매에서는 칩 차감 근거인 입찰과 판정이 달라질 수 있다.

## 수정 방향

제출 저장과 마감이 같은 DB 잠금/트랜잭션 규약을 사용하도록 한다. 제출은 현재 입력 세대·라운드·단계·방 상태와 참가 자격을 저장 시점에 검증하고, 마감은 확정된 제출 집합만 읽어 정산해야 한다. 단순히 UPSERT 직전에 방을 한 번 더 읽는 방식으로는 경쟁 구간이 없어지지 않는다. 001의 세대 식별과 003의 정산 원자성을 함께 고려한다.

## 완료 기준

- [ ] 마감과 겹친 제출은 “확정 결과에 반영” 또는 “거절되어 저장되지 않음” 중 하나로만 귀결된다.
- [ ] 공개 결과·저장된 제출·참가자 자신의 선택이 서로 일치한다.
- [ ] 마감 중 문제 변경이나 다음 입력 단계 진입이 끼어들어도 과거 제출이 섞이지 않는다.
- [ ] 소수결과 공통 `submitMove` 모두 동일한 계약을 적용한다.
- [ ] 지연 작업을 통제하는 회귀 테스트와 Supabase 트랜잭션 검증을 추가한다.
