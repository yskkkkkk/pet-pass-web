# 004 — 참가 조건 검증과 삽입 사이의 경쟁으로 정원·시작 제한 우회

**우선순위:** P1

**분류:** 구현 결함 / 공통 대기실

**상태:** 미해결

## 근거

- `api/game.js:102-130`: `room.status`, 참가자 수를 검사한 뒤 별도로 `addPlayer`를 호출한다.
- `lib/game/store.js`의 `addPlayer`: 방이 대기실인지와 정원을 삽입 시점에 확인하지 않는다.
- `supabase_game_schema.sql`의 `game_players`: 닉네임 중복 제약은 있지만 대기실/정원 제약은 없다.
- `public/game/games.js`의 `maxPlayers`와 계획서의 게임별 최대 인원은 참가 처리에서 지켜져야 한다.

## 재현과 영향

**정원 경쟁:** 격리 테스트에서 최대 인원을 4로 설정하고 3명이 있는 방에 서로 다른 닉네임 2개로 동시에 참가했다. 두 요청이 모두 200이고 실제 참가자는 5명이 되었다. 운영 소수결의 현재 최대값은 200이지만 같은 로직을 사용하므로 문제 구조는 동일하다.

**시작 경쟁:** 참가 요청이 대기실 검증을 통과한 뒤 `addPlayer` 직전에 대기하도록 했다. 진행자가 게임을 시작한 뒤 삽입을 재개해도 신규 참가가 200으로 성공하고 투표 중 방에 새 참가자가 생겼다.

새 게임에서는 시작 시 칩·카드·주사위를 초기화한 목록과 실제 참가자가 달라질 수 있다. 특히 인원에 따라 덱 크기나 과반 분모가 달라지는 규칙에 영향을 준다.

## 수정 방향

대기실 상태·정원 검사·참가 삽입을 방 단위로 직렬화하고, 게임 시작이 같은 잠금 규약을 사용하도록 한다. 서버리스 인스턴스 안의 JS 잠금만으로는 다른 인스턴스의 요청을 막을 수 없다. 기존 토큰에 의한 복귀는 신규 참가와 구분하여 유지한다.

## 완료 기준

- [ ] 남은 자리 1개에 N명이 동시에 참가해도 신규 참가 성공은 1건뿐이다.
- [ ] 시작과 경합한 신규 참가자는 시작 시 명단에 포함되거나 명시적으로 거절된다.
- [ ] 거절된 참가자 행이나 미초기화된 참가자 상태가 남지 않는다.
- [ ] 이미 참가한 기기의 유효한 토큰 복귀는 게임 중에도 가능하다.
- [ ] 메모리 계약 테스트와 실제 DB의 동시 참가/시작 테스트를 추가한다.
